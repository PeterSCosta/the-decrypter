# Recomendação — aba **Áudio** do The Decrypter

*(consolidação das 5 frentes pesquisadas; números vêm do levantamento, o que não foi verificado está marcado **não confirmado**)*

## 1. A resposta em três linhas

1. **Comece pelo que o navegador já faz de graça**: Web Audio (espectrograma, DTMF por Goertzel, Morse por tom, síntese para conferir hipótese) + `SpeechRecognition.start(audioTrack)` para voz→texto — zero chave, zero cartão, zero backend, zero bytes de bundle, e é aqui que mora a maior parte das provas.
2. **Depois, um único endpoint novo no .NET** (`/api/audio/transcrever` → Groq Whisper large-v3-turbo: **8 h de áudio por dia, recorrente, sem cartão**) porque a Web Speech é Chrome/Edge-only e roda em tempo real.
3. **Só então música**: `shazamio-core` (WASM no navegador + proxy .NET) para reconhecer trecho ruidoso, com **AcoustID** em paralelo (CORS aberto, chamada direta do navegador) e **LRCLIB** para puxar a letra inteira para o Decodificador.

## 3. O caminho recomendado, detalhado

### Fase 0 — navegador puro (nenhuma chave, nenhum backend)

O grosso do valor. Nada aqui depende de cadastro, cota ou rede.

- **Entrada de arquivo** → `AudioContext.decodeAudioData()` → PCM Float32 → alimenta `calcularStft` (`src/features/audio/stft.ts`) e `goertzel()` (`src/features/audio/fft.ts:135`).
- **DTMF**: tabela 697/770/852/941 Hz × 1209/1336/1477/1633 Hz; o Goertzel já está escrito, falta a máquina de estados de dígitos.
- **Morse por tom**: envelope + limiar → `.`/`-`/espaço → entra direto no decoder já registrado em `src/features/decoder/engine/codecs.ts:293` (`single("morse", …, decodeMorse, encodeMorse)`).
- **Síntese para conferir hipótese**: `OscillatorNode` + `OfflineAudioContext` + um encoder WAV de ~40 linhas (RIFF escrito à mão — nenhum navegador grava WAV pelo MediaRecorder). De brinde: sintetizar um DTMF conhecido e cobrar a resposta do Goertzel vira teste em `fundacao.test.ts`.
- **STFT acima de ~3 s vai para Worker** (Vite tem Worker nativo), devolvendo `Uint8Array` transferível, não `Float32Array`.

**Duas armadilhas medidas que precisam de defesa no código:**
- `decodeAudioData` **reamostra em silêncio** para a taxa do `AudioContext`, e `AudioBuffer.sampleRate` já é a taxa do contexto — a taxa original do arquivo não é exposta por API nenhuma. Um tom de 30 kHz num arquivo de 96 kHz some num contexto de 48 kHz, e a faixa alta aparece vazia com toda a cara de estar correta.
- `decodeAudioData` faz **detach do ArrayBuffer de entrada** (176.444 → 0 bytes, medido). Quem for ler os bytes crus depois (container, LSB) recebe comprimento 0, sem erro, passando por TypeScript e Biome. Defesa: `slice(0)` antes.

### Fase 1 — voz → texto sem chave (`SpeechRecognition.start(audioTrack)`)

```
const el = new Audio(URL.createObjectURL(file));
el.addEventListener("canplay", () => {
  const track = el.captureStream().getAudioTracks()[0];
  el.play();
  rec.start(track);            // Chrome/Edge 135+
});
```

- `rec.lang = "pt-BR"`, `continuous = true`, `interimResults = true` (a sessão da nuvem corta perto de 60 s).
- **Detecção de capacidade obrigatória**: sem `"captureStream" in HTMLMediaElement.prototype` e sem `SpeechRecognition`, o botão **some**, não falha. Safari não tem `captureStream`; Firefox não aceita `audioTrack`.
- **Offline quando der**: `await SpeechRecognition.available({ langs: ["pt-BR"], processLocally: true })` → `"downloadable"` dispara `install()` com barra de progresso; só então `rec.processLocally = true`. Trate `"downloading"` com timeout — há issue aberta do Chromium (444393111) no macOS e relato de instalação pendurada no Brave.
- **Ganho de graça**: `rec.phrases` (Chrome 142+) aceita viés contextual — injete o vocabulário da prova (ruas de Blumenau/Itajaí, termos da gincana).
- O texto sai normalizado (maiúsculas, acentos, sem pontuação). Isso é **bom** para as ~100 cifras, mas **mostre o texto cru e deixe editar** antes de mandar para o Decodificador: se a prova esconder a resposta na grafia exata, a normalização a destrói.

### Fase 2 — backend .NET (o padrão já está pronto no repo)

Um controller, dois gateways. Copie exatamente o desenho do what3words/Nominatim:

**Backend** (`~/Repos/the-decrypter-api`):

1. `src/TheDecrypter.Domain/Gateways/ISpeechToTextGateway.cs` — espelha `IWhat3WordsGateway.cs`:
   `Task<string?> TranscribeAsync(Stream audio, string fileName, string lang, CancellationToken ct)`.
2. `src/TheDecrypter.Http/Gateways/GroqSpeechGateway.cs` — mesmo molde do `What3WordsGateway.cs`: chave lida de `config["Gateways:Groq:Key"]`, `MultipartFormDataContent` com `file`, `model=whisper-large-v3-turbo`, `language=pt`, `response_format=text`; `Authorization: Bearer`. **A chave vai no header, nunca na query-string** — é a decisão já registrada no comentário do gateway do w3w ("query-string vaza em logs de proxy/CDN").
3. `src/TheDecrypter.Http/HttpDependencyInjection.cs` — mais uma linha no mesmo padrão:
   `services.AddHttpClient<ISpeechToTextGateway, GroqSpeechGateway>(c => Configure(c, groq)).AddResilienceHandler("groq", b => AddResilience(b, 20));` — o `20` casa com os 20 RPM do free tier do Groq, do mesmo jeito que o `30` do Nominatim casa com ~1 req/s. O `AddResilience` já traz timeout, retry exponencial com jitter, circuit-breaker e `TokenBucketRateLimiter`.
   Para o MusicBrainz, a cópia é literal a do Nominatim: `c.DefaultRequestHeaders.UserAgent.ParseAdd(userAgent)` + `AddResilience(b, 30)`.
4. `src/TheDecrypter.Api/Controllers/AudioController.cs` — `[ApiController] [Route("api/audio")] [Authorize]`, recebendo `IFormFile` e devolvendo `{ text }`. Reaproveite o `Wrap<T>` do `LookupsController` (503 + `{ message }` quando o upstream cai) e o `UpstreamErrorMiddleware` que já existe.
5. **Cache**: `TheDecrypter.Cache` (Redis) já está de pé — chaveie a transcrição pelo **hash do arquivo**. É o que impede um mesmo áudio de comer a cota duas vezes. O `OutputCache(PolicyName = "lookups")` do `LookupsController` não serve aqui (é POST multipart), então o cache tem que ser explícito no serviço.
6. Segundo endpoint, `POST /api/audio/shazam`: recebe **só a assinatura** (`data:audio/vnd.shazam.sig;base64,…` gerada no navegador — texto leve) e faz o POST em `amp.shazam.com/discovery/v5/<lang>/<country>/web/-/tag/<uuid-v4>`. Esse salto **tem** que ser no servidor: `amp.shazam.com` não devolve `access-control-allow-origin`.

**Front** (`~/Repos/the-decrypter`):

- Chame por `apiFetch` (`src/lib/api.ts`), que já injeta o `Bearer` e trata 401/429 — mesmo caminho de `src/lib/what3words.ts`.
- ⚠️ **Gotcha real do helper**: `apiFetch` faz `if (init.body && !headers.has("Content-Type")) headers.set("Content-Type", "application/json")`. Com `FormData` isso **quebra o multipart** (o boundary não é gerado). Ou passe `headers` com o Content-Type já definido para o `fetch` recalcular, ou ajuste o helper para pular o default quando `init.body instanceof FormData`.
- Reduza o arquivo **antes de subir**: converta para mono 16 kHz com `OfflineAudioContext` — o teto de 25 MB do free tier do Groq deixa de existir na prática (~4 h de áudio).
- Aba `audio` já desenhada em `docs/PLANO-AUDIO.md`: entra por `lazy()` no `<Suspense>` existente, para o Decodificador (aba padrão) não pagar o chunk.

### Fase 3 — música e som (sob demanda, chunk separado)

- `shazamio-core` (**602 KB gzip**, MIT, última publicação abr/2024) por `await import()` só quando a aba abrir; a assinatura vai para `/api/audio/shazam`.
- **AcoustID em paralelo, direto do navegador** — `api.acoustid.org` responde `access-control-allow-origin: *` no OPTIONS e no GET; a chave `client` é pública por design. WASM ~116 KB gzip (compilar `rusty-chromaprint` com wasm-pack) **ou**, mais barato de manter, rodar o binário `fpcalc` no .NET via `Process` — custo zero no bundle.
- Normalize as duas (mais AudD) num formato único `{ titulo, artista, album, fonte, confianca }` e ponha **"mandar para o Decodificador"** em cada linha. O título costuma ser a resposta literal — mas às vezes ainda passa por uma cifra (acróstico das iniciais, o título em ROT13, o número da faixa).
- Som ambiente: **comece pelo MediaPipe/YAMNet (~11 MB)**, não pelo AST. As duas frentes da pesquisa divergiram aqui, e o desempate é peso: o AST ganha em qualidade (mAP 0,459 vs 0,306) mas custa 51–91 MB. YAMNet como modo padrão, AST como "modo preciso" opcional. O caminho antigo via TensorFlow.js/TF Hub **está morto** (a URL do modelo tfjs responde 403 hoje) — no MediaPipe o `.tflite` vem do pacote npm.

## 4. O que dá para fazer HOJE, sem chave nenhuma ⭐

Esta é a seção que importa: **tudo abaixo funciona sem cadastro, sem cota e sem cartão.**

**Sem rede nenhuma (offline de verdade):**
- Espectrograma, inversão, mudança de velocidade, separação de canais L/R (revela mensagem em antifase — pedido explícito do dono).
- **DTMF → dígitos** e **Morse por tom → texto**, ambos determinísticos: não inventam nada e caem direto na Cadeia (`áudio → DTMF → A1Z26 → CEP`).
- Leitura de chunks RIFF, LSB (já existe em `src/features/audio/lsb.ts`).
- **Síntese** de tons, DTMF, Morse e varreduras + WAV baixável, para conferir hipótese e para testar os próprios detectores.
- `speechSynthesis` para "ouvir a hipótese em voz alta" — 15 linhas. **Limite duro: o áudio não é capturável**, então isso é botão de ouvir, nunca fonte de dados.
- **Transcrição pt-BR sem nenhum serviço**: `SpeechRecognition` com `processLocally = true` (Chrome 139+, pt-BR na lista on-device — o modelo é gerenciado pelo próprio navegador, custo de bundle **zero**). Atenção: o **Edge** tem implementação própria e a lista local dele é **pt-PT, não pt-BR**.

**Sem chave, mas com rede (CORS `*` verificado — chamada direta do navegador):**

| Serviço | Chamada | Serve para |
|---|---|---|
| **LRCLIB** | `GET https://lrclib.net/api/search?track_name=&artist_name=` → `/api/get/{id}` | letra inteira em texto puro → Decodificador |
| **lyrics.ovh** | `GET https://api.lyrics.ovh/v1/{artista}/{titulo}` | plano B do LRCLIB |
| **iTunes Search** | `GET https://itunes.apple.com/search?term=&entity=song&country=BR` | limpar o título torto que sai da transcrição |
| **iNaturalist** | `GET https://api.inaturalist.org/v1/taxa?q={científico}&locale=pt-BR` | `Ramphastos toco` → `Tucano-toco` |
| **Discogs** | `GET https://api.discogs.com/database/search?q=` sem token | prensagem, gravadora, nº de catálogo (25/min por IP) |
| **AcoustID** | `GET https://api.acoustid.org/v2/lookup?client=&fingerprint=&duration=&meta=recordings` | reconhecimento de música (a `client` é chave pública gratuita, vai na query por design) |

**Modelos locais, sem chave:** MediaPipe/YAMNet (~11 MB), AST (51–91 MB), BirdNET tfjs (~51,3 MB) — todos baixados uma vez e cacheados, servidos do **próprio domínio** (`public/` + o `nginx.conf` que já está no repo), **nunca de CDN**.

## 6. Riscos

**Dependência de terceiro num app que se orgulha de funcionar offline.**
A Fase 0 inteira e a Fase 1 rodam sem rede — é isso que preserva a identidade da bancada. Toda chamada externa é **enriquecimento**, nunca caminho único. Regra de projeto: **a aba Áudio nunca fica inutilizável** quando um serviço cai. Concretamente: se o `shazamio-core` quebrar (endpoint interno do Shazam, sem contrato público, pacote parado desde abr/2024), o AcoustID assume sozinho; se o Groq der 429, cai para o Cloudflare Workers AI ou para a Web Speech local.

**Quando a cota estoura.**
- Groq: 429 é o sinal, e a cota é **compartilhada por toda a instância** — um áudio longo de um usuário come a de todos. O cache por hash de arquivo no Redis não é opcional.
- AudD: **300 fichas que não renovam.** Nunca automático — botão explícito com **contador de fichas restantes na tela**, e mensagem clara quando zerar. (Para validar a integração sem gastar ficha, `api_token=test` funciona e devolve reconhecimento real; os limites desse token compartilhado não são documentados — não construa em cima dele.)
- Deepgram (US$ 200) e AssemblyAI (US$ 50): créditos **únicos**. São reserva estratégica, não base. Quando zeram, a AssemblyAI **pausa a API** até você pôr cartão.
- MusicBrainz: o 1 req/s vale para o IP do **seu servidor** — todos os usuários dividem o mesmo balde.

**Privacidade — precisa de aviso na interface.**
- Web Speech **sem** `processLocally` manda o áudio da prova para os servidores do Google. É "sem API" no sentido de não ter chave, **não** no sentido de não ter terceiro.
- Groq, Cloudflare, AudD e Shazam recebem o arquivo (ou a assinatura). O free tier do Groq **não dá garantia de retenção zero**.
- Desenho recomendado: cada rota de transcrição/reconhecimento exibe um rótulo fixo — *"local"* (verde) ou *"o áudio sai da sua máquina"* (âmbar) — e a nuvem só é usada depois que o caminho local falhou ou foi recusado. Detalhe bom do fingerprint: com AcoustID/Chromaprint sobe **só a impressão digital**, não o áudio.

**Alucinação — o risco mais perigoso para uma oficina de cifras.**
Whisper **inventa texto** em silêncio e em ruído puro. Um texto inventado que entra no Decodificador vira 100 hipóteses de cifra em cima de nada — precisamente a "máquina de mentira" que o `PLANO-AUDIO.md` diz que a bancada não pode ser. Mitigação: `vad_filter`/`no_speech_threshold` onde existir, rótulo visível de **transcrição automática**, e **confirmação humana antes do fan-out**. O mesmo vale para os classificadores: eles devolvem `Siren`, `Bell`, `Bird` — rótulos genéricos em inglês, que são **pista, não resposta**. Sempre top-5 com a confiança à vista, nunca só o topo.

**Colisão arquitetural conhecida.**
Ligar **COOP/COEP** (para threads do ONNX Runtime ou do ffmpeg.wasm multi-thread) muda o comportamento de **toda** a página e pode quebrar os tiles do Leaflet e qualquer recurso cross-origin sem CORP. `credentialless` resolve no Chrome/Firefox mas **não existe no Safari** — ou seja, a otimização pode derrubar o mapa no iPhone, exatamente o cenário "equipe na rua". Se o Whisper local entrar, ele roda **sem** threads (1 thread, mais lento, mas funciona) até isso ser medido.

**Licenças que contaminam.**

## Detalhamento por categoria

### Reconhecimento de MÚSICA (que música é esta?)

**Recomendada:** **Empilhar três, nesta ordem — porque nenhuma sozinha resolve o caso da gincana.**

O fato decisivo que separa as opções não é preço, é **o que cada uma consegue casar**. Chromaprint/AcoustID identifica *áudio quase idêntico* — o mesmo master, o arquivo inteiro, desde o começo. A documentação oficial diz que ele "troca precisão e robustez por desempenho de busca", e a análise comparativa mede ~60% de acerto com ruído rosa a 3 dB. Numa gincana o áudio quase nunca é o master: é um trecho de 20s do meio da música, recortado, re-encodado, às vezes gravado do ambiente. **Nesse cenário o AcoustID falha e o Shazam acerta.** Então:

**1º — Shazam não-oficial via `shazamio-core` (WASM) + proxy no .NET.** É o único caminho que é ao mesmo tempo gratuito ilimitado, sem cartão, sem cadastro *e* com qualidade de reconhecimento real (trecho do meio, ruído, gravação de ambiente). Custo: 602 KB gzip de WASM carregado sob demanda (só quando o usuário abre a aba Áudio — não entra no bundle inicial) e um endpoint novo no backend. É a maior taxa de acerto por real gasto, de longe.

**2º — AcoustID, logo em seguida, porque é quase de graça implementar.** Confirmei por curl que `api.acoustid.org` responde `access-control-allow-origin: *` — **o navegador chama direto, sem passar pelo backend**. É ilimitado, sem cartão, 100% legítimo e open source. Ele ganha exatamente onde o Shazam às vezes tropeça: arquivo original inteiro, faixa obscura, gravação que existe no MusicBrainz mas não no catálogo comercial. Some 116 KB gzip de WASM. Rode os dois em paralelo e mostre as duas respostas.

**3º — AudD como "queimar uma ficha", com botão manual.** 300 requisições únicas, sem cartão. É boa demais para gastar automaticamente, e boa demais para não ter. Deixe um botão explícito "tentar com AudD" para quando os dois primeiros falharem. Coloque um contador visível das fichas restantes.

**Descarte ACRCloud, Shazam-via-RapidAPI, Spotify e Deezer como reconhecedores.** ACRCloud é trial de 14 dias com cota não publicada — não dá para planejar em cima. RapidAPI dá 100–500 req/mês e a maioria dos wrappers nem faz detecção por áudio. Spotify não reconhece áudio e desde fev/2026 exige conta Premium só para criar o app. Deezer não reconhece áudio e nem CORS tem.

**Guarde Deezer/iTunes/MusicBrainz para outro papel:** enriquecer e confirmar o título depois de reconhecido. iTunes e MusicBrainz responderam `access-control-allow-origin: *` no meu teste — o navegador chama direto, de graça, sem chave.

**Ponto de arquitetura que vale para as três:** o valor que interessa ao Decodificador é o **título em texto**. Normalize a resposta das três fontes num único formato (`{titulo, artista, album, fonte, confianca}`) e mande `titulo` — e opcionalmente `artista - titulo` — direto para o campo do Decodificador. O título costuma ser a resposta literal da prova, mas às vezes ele ainda passa por uma cifra (acróstico das iniciais, o título em ROT13, o número da faixa). Ter o texto normalizado e um botão "mandar para o Decodificador" é o que fecha o ciclo.

**Uma pegadinha de decodificação de áudio:** nenhuma das opções precisa de `ffmpeg.wasm` (que sozinho passa de 25 MB). O `shazamio-core` decodifica o arquivo internamente (Symphonia embutido — é o que explica o 1,5 MB). Para o AcoustID, o `decodeAudioData`/`OfflineAudioContext` nativo do navegador entrega PCM Float32 de mp3/wav/m4a/ogg de graça, peso zero. Use o nativo e reamostre com `OfflineAudioContext` para alimentar o Chromaprint.

- **AcoustID + Chromaprint (WASM) + MusicBrainz** — O caminho totalmente livre e open source. O Chromaprint calcula uma impressão digital acústica do áudio; a API do AcoustID casa essa impressão com um ID e, com meta=recordings, devolve título, artista e álbum vindos do MusicBrainz — já em texto, pronto para o Decodificador.
  - https://acoustid.org/webservice
  - gratuito: `sim-ilimitado` · cartão: não · limites: Plano não-comercial: buscas ILIMITADAS, limitado a 3 requisições/segundo. Sem cartão. Uso comercial exige plano pago (€50/mês por 1M de buscas, €100/mês por 15M, €500/mês por 150M), com trial de 10k buscas. Chave de aplicação gratuita registrando em acoustid.org/new-application. WASM medido por mim no artefato do demo oficial: 301.013 bytes crus, 115.848 bytes gzipados (~116 KB), mais o glue do wasm-bindgen (poucos KB).
  - integra: DIRETO DO NAVEGADOR — confirmei por curl que https://api.acoustid.org/v2/lookup responde 'access-control-allow-origin: *' tanto no OPTIONS quanto no GET. Não precisa do backend .NET. Fluxo: (1) arquivo -> ArrayBuffer -> AudioContext.decodeAudioData() -> PCM Float32 (nativo, peso zero, cobre mp3/wav/m4a/ogg); (2) reamostrar com OfflineAudioContext e alimentar o WASM do Chromaprint, que devolve a fingerprint comprimida em base64; (3) GET/POST em /v2/lookup com client=<chave>, fingerprint=<base64>, duration=<segundos inteiros> e meta=recordings; (4) ler results[].recordings[].title e .artists[].name. A chave 'client' do AcoustID é pública por design (vai no parâmetro de query, o próprio demo oficial faz isso no navegador), então não há segredo a proteger — mas se quiser blindar contra abuso da sua cota, o proxy no .NET já existente serve. Sobre o WASM: NÃO existe pacote npm mantido. Os do npm estão mortos (chromaprint-wasm 0.1.2 de 2018, 95 KB; chromaprint e chromaprint.js em JS puro de 2015/2017). O caminho vivo é compilar github.com/darksv/rusty-chromaprint com wasm-pack (ele pede PCM intercalado + sample rate + nº de canais, não decodifica áudio) ou versionar o artefato do demo em rusty-chromaprint-wasm.janis.me. Alternativa sem WASM nenhum: rodar o binário fpcalc no backend .NET via Process — mais simples de manter, custo zero no bundle.
  - esforço: Médio-alto se for pelo WASM (compilar rusty-chromaprint com wasm-pack, versionar o .wasm, amarrar decodificação + reamostragem). Baixo se rodar fpcalc no backend .NET. A chamada HTTP em si é trivial. · risco: O RISCO PRINCIPAL É DE COBERTURA, NÃO DE COTA. O Chromaprint foi feito para 'identificar áudio quase idêntico' e o próprio README admite que 'troca precisão e robustez por desempenho de busca'. Casos de uso declarados: identificar arquivo inteiro, achar duplicatas, monitorar stream. Uma análise comparativa mede ~60% de acerto com ruído rosa a 3 dB, e há relatos de que a consulta precisa vir do INÍCIO do áudio (o fpcalc, por padrão, só analisa os primeiros 120s). Tradução para a gincana: se a prova entregar o arquivo original inteiro, funciona muito bem; se entregar um trecho de 20s do meio da música, um recorte re-encodado ou uma gravação de celular no ambiente, tende a NÃO casar. Segundo risco: a base é colaborativa e atrelada ao MusicBrainz, então música brasileira regional, sertanejo antigo ou funk pode simplesmente não estar lá. Terceiro: 'não-comercial' não é definido em detalhe — para uma ferramenta interna de gincana isso é confortável, mas vale registrar a intenção.

- **Shazam não-oficial (shazamio-core WASM + amp.shazam.com)** — Reimplementação em Rust/WASM do algoritmo de assinatura do próprio Shazam. Gera localmente a assinatura (data:audio/vnd.shazam.sig;base64,...) a partir dos bytes do arquivo e consulta o endpoint interno do Shazam. É reconhecimento com qualidade Shazam de verdade — aguenta trecho do meio da música, ruído e gravação de ambiente. Sem chave, sem cadastro, sem cota.
  - https://www.npmjs.com/package/shazamio-core
  - gratuito: `sim-ilimitado` · cartão: não · limites: Sem chave e sem cota publicada — na prática limitado pelo que o endpoint do Shazam tolera de um mesmo IP (não confirmado; presuma que há throttling e faça backoff). Peso medido por mim no tarball 1.3.1: web/shazamio-core_bg.wasm = 1.538.052 bytes crus, 602.498 bytes gzipados (~602 KB). Licença MIT. Última publicação: abril/2024 — sem atualização desde então.
  - integra: HÍBRIDO — WASM no navegador, chamada HTTP pelo backend .NET. A parte cara (assinatura) roda no cliente; a parte bloqueada por CORS roda no servidor. Fluxo: (1) no navegador, importar de 'shazamio-core/web' e chamar recognizeBytes(uint8Array, offset, seconds) — ele recebe os BYTES CRUS do arquivo e decodifica internamente (Symphonia embutido, por isso 1,5 MB), devolvendo DecodedSignature[] com a propriedade .uri; (2) mandar essa .uri (é só texto base64, leve) para um endpoint novo no .NET; (3) o .NET faz POST em https://amp.shazam.com/discovery/v5/<lang>/<country>/web/-/tag/<uuid-v4-aleatório> com a assinatura no corpo; (4) extrair track.title e track.subtitle do JSON e devolver ao front. O passo 3 TEM que ser no backend: testei amp.shazam.com com header Origin e não veio nenhum access-control-allow-origin, então o navegador bloqueia. Carregue o WASM com import dinâmico só quando a aba Áudio abrir, para não pesar o bundle inicial. Para copiar a montagem do corpo da requisição e os headers, veja node-shazam (GPL-2.0 — leia só como referência, não vendorize dentro de um projeto com licença incompatível).
  - esforço: Médio. O WASM vem pronto do npm (não precisa compilar nada), a API é uma função só. O trabalho real é o endpoint proxy no .NET e imitar corretamente os headers/corpo que o cliente web do Shazam manda. · risco: É UM CAMINHO NÃO-OFICIAL — esse é o risco de verdade, e ele é duplo. Técnico: o endpoint é interno do Shazam, não tem contrato público e pode mudar ou passar a exigir assinatura/atestação a qualquer momento, derrubando a integração sem aviso; o pacote está parado desde abr/2024, então se quebrar talvez ninguém conserte e sobra para você. Jurídico/ToS: usar endpoint interno da Apple/Shazam de forma programática quase certamente contraria os termos de uso deles — para uma ferramenta interna de gincana o risco prático é baixo (no máximo bloqueiam seu IP), mas não coloque isso num produto público nem em nada que gere receita. Mitigação obrigatória: trate como best-effort, com fallback automático para AcoustID e botão manual para AudD, para que a aba Áudio nunca fique inutilizável quando isso cair. Some 602 KB gzip — aceitável só porque é carregado sob demanda.

- **AudD.io** — API comercial de reconhecimento musical. Recebe o arquivo (ou uma URL) e devolve artist, title, album, release_date, label, timecode e song_link. Reconhecimento robusto de verdade: pega trecho curto, áudio ruidoso e gravação de ambiente.
  - https://docs.audd.io/
  - gratuito: `trial` · cartão: não · limites: 300 requisições grátis na inscrição, SEM cartão. É crédito ÚNICO, não renova por mês. Depois: US$5 por 1.000 requisições no pré-pago, caindo até US$2/1.000 por volume, sem mensalidade mínima. Arquivo máximo: 10 MB no endpoint padrão (arquivos maiores/longos só no endpoint enterprise). Monitoramento de stream é cobrado à parte (US$45/mês por stream concorrente).
  - integra: PELO BACKEND .NET, apesar de o CORS permitir o navegador. Testei e https://api.audd.io/ responde 'access-control-allow-origin: *' — tecnicamente o navegador chama direto. NÃO FAÇA ISSO: o api_token seria embutido no JS e qualquer um torraria suas 300 fichas. Como o backend .NET já é proxy de what3words/BrasilAPI/Nominatim, o padrão está pronto: o token fica em configuração no servidor, o front faz POST multipart em /api/audio/audd com o arquivo, e o .NET repassa. Chamada upstream: POST https://api.audd.io/ em multipart/form-data com api_token=<token> e o arquivo no campo 'file' (ou url=<link> em vez do arquivo). A resposta útil é result.title e result.artist. Detalhe verificado na prática: api_token=test FUNCIONA — mandei um POST com o token literal 'test' e voltou um reconhecimento real ({artist: 'Tears For Fears', title: 'Everybody Wants To Rule The World', ...}). Serve para você validar toda a integração antes de gastar qualquer ficha; os limites desse token compartilhado não são documentados, então não construa em cima dele.
  - esforço: Baixo. É um POST multipart e dois campos no JSON de resposta. O endpoint proxy no .NET sai em uma sentada. · risco: A cota é o problema: 300 requisições são um orçamento pequeno e que NÃO se renova. Numa gincana com várias equipes e várias tentativas por prova, isso evapora rápido — então não pode ser a chamada automática, tem que ser um botão consciente com contador de fichas restantes na tela. Quando acabar, a aba silenciosamente para de funcionar se você não tratar o erro de cota com mensagem clara. Risco secundário: preço por requisição pode mudar, e como o cadastro não pede cartão você não corre risco de cobrança surpresa — mas também não há como estourar a cota 'só um pouquinho'.

- **ACRCloud** — API comercial de reconhecimento por fingerprint, das mais fortes do mercado (usada por plataformas grandes). Reconhece música gravada, e em planos específicos também versões ao vivo, covers e cantarolado. Devolve título, artistas e álbum.
  - https://www.acrcloud.com/music-recognition/
  - gratuito: `trial` · cartão: não · limites: Trial de 14 dias, sem cartão. A COTA DE REQUISIÇÕES DO TRIAL NÃO ESTÁ CONFIRMADA — os termos só dizem que valem os 'limites de assinante publicados no site', e a tabela de preços fica atrás do login do console; a página pública de pricing não traz número nenhum. Os SDKs usam ~10 segundos de áudio por requisição.
  - integra: OBRIGATORIAMENTE PELO BACKEND .NET — não há escolha aqui. A autenticação é access_key + access_secret com assinatura HMAC do corpo da requisição; o access_secret não pode encostar no navegador, e a assinatura precisa ser calculada no servidor. Encaixa no padrão de proxy que já existe: o front manda o arquivo para /api/audio/acr, o .NET monta a assinatura HMAC e chama o endpoint de identificação do host da sua região. Como o serviço usa só ~10s de áudio, o backend deve recortar o trecho antes de enviar.
  - esforço: Alto — e o esforço é mal investido. Além do proxy, você tem que implementar a assinatura HMAC corretamente (fonte clássica de erro 3001/3003), escolher host por região e criar conta com trial que expira. É o dobro de trabalho do AudD para um benefício que você não consegue nem dimensionar antes de assinar. · risco: O risco maior é não conseguir planejar: sem cota publicada, você integra às cegas e só descobre o limite quando bate nele. Somado a isso, o trial de 14 dias tem prazo de validade, então a integração naturalmente morre duas semanas depois do dia em que você a construiu — péssimo para uma ferramenta que fica parada entre uma gincana e outra. Para virar permanente exige cartão. Recomendo não integrar agora; deixe anotado como plano B caso o volume um dia justifique um contrato pago.

ATENÇÃO: a maioria faz apenas BUSCA POR TEXTO e paradas de sucesso (metadados), não detecção a partir de áudio. Os que têm endpoint de detecção normalmente exigem que você já mande a assinatura do Shazam pronta em base64 — ou seja, você continua precisando gerar a assinatura localmente, e aí o wrapper vira só um intermediário cobrado.

  - integra: PELO BACKEND .NET — e isso eu verifiquei, contra o que muito blog afirma. Chamei https://api.deezer.com/search com header Origin e a resposta traz access-control-allow-headers, -methods, -credentials e -max-age, MAS NÃO TRAZ access-control-allow-origin.   - esforço: Muito baixo — um GET sem autenticação atrás do proxy. Mas só depois que o reconhecimento estiver funcionando; sozinho não resolve nada. · risco: O risco é de expectativa: é fácil olhar a lista e achar que 'Deezer' cobre o caso de uso, quando ele não reconhece áudio nenhum. Riscos menores: o limite de 50/5s é generoso mas real; o endpoint público é informal e a Deezer já apertou acesso de terceiros no passado; a resposta traz cookies e proteção Akamai (vi headers _abck/bm_sz no meu teste), o que sugere que uso automatizado pesado pode ser barrado. - **Spotify Web API** — Catálogo e metadados por busca de texto. NÃO FAZ RECONHECIMENTO DE ÁUDIO — nunca fez, e não existe endpoint que receba arquivo. Para esta categoria, não serve.

- **iTunes Search API + MusicBrainz (busca por texto)** — Não reconhecem áudio, mas fecham o ciclo depois do reconhecimento: transformam um título parcial, mal grafado ou um fragmento de letra numa grafia canônica de título/artista/álbum — que é exatamente o texto que o Decodificador precisa receber.

Zero backend, zero chave, zero peso de bundle. iTunes: GET https://itunes.apple.com/search?term=<termo>&entity=song&limit=5, ler results[].trackName e .artistName. MusicBrainz: GET https://musicbrainz.org/ws/2/recording?query=<termo>&fmt=json&limit=5 com User-Agent próprio (ex.: 'TheDecrypter/1.0 (contato)'), ler recordings[].title. Encaixe natural na aba Áudio: (a) depois de transcrever uma voz, jogar a frase aqui para ver se ela é o título de uma música; (b) depois de reconhecer, normalizar a grafia antes de mandar ao Decodificador; (c) como busca manual quando o usuário já suspeita do título e quer confirmar.
  - esforço: Muito baixo — dois fetch diretos do navegador, sem proxy, sem chave, sem segredo a proteger. É o melhor retorno por linha de código desta lista inteira. · risco: Baixo. O ponto de atenção é ético/operacional, não técnico: o MusicBrainz bloqueia quem ignora o limite de 1 req/s ou omite o User-Agent — então serialize e faça debounce. O limite do iTunes não é contratual e a Apple pode apertar sem aviso. E lembre que isso é BUSCA, não reconhecimento: casa texto com texto, e vai devolver resultado plausível mesmo para uma consulta ruim, então mostre as 5 opções ao usuário em vez de assumir a primeira como verdade.

### Voz para TEXTO (transcrição de áudio → texto)

**Recomendada:** **Combinação de três camadas, nesta ordem.**

**1) Web Speech API com `start(audioTrack)` — a primeira a implementar.** É a única opção que resolve "arquivo → texto" com ZERO chave, ZERO backend, ZERO custo e ZERO peso no bundle. Descoberta importante desta pesquisa: desde o **Chrome/Edge 135** o `start()` aceita um `MediaStreamTrack`, e o próprio exemplo do MDN mostra `new Audio(arquivo)` → `captureStream()` → `recognition.start(track)`. Ou seja, a limitação clássica de "só microfone" **acabou**. Limitações reais: só Chrome/Edge desktop, roda em tempo real (áudio de 3 min = 3 min de espera), e a sessão da nuvem do Google corta perto de 60 s (contornável com `continuous=true` + reinício, ou com `processLocally=true` no Chrome 139+, que tem pacote **pt-BR** on-device). Para a gincana — clipes curtos de fala — isso cobre a maioria dos casos sem gastar nada.

**2) Groq Whisper Large v3 Turbo atrás do backend .NET — o burro de carga.** É o melhor custo-benefício disponível: **28.800 segundos de áudio por dia (8 horas/dia), renovando todo dia, sem cartão de crédito**, 2.000 requisições/dia. Não é um crédito único que acaba — é cota diária recorrente, exatamente o que uma oficina de cifras precisa. Whisper large-v3-turbo é multilíngue (pt-BR nativo), roda a 216× tempo real (um áudio de 5 min volta em ~1,5 s) e devolve texto puro pronto para cair no Decodificador. O teto de 25 MB por arquivo no free tier é o único aperto, e se resolve convertendo para FLAC/Opus 16 kHz mono no navegador antes de subir. Encaixa perfeitamente no padrão que já existe no repo (`TheDecrypter.Http/Gateways/What3WordsGateway.cs` + `TheDecrypter.Api/Controllers/`): chave no servidor, front chama `/api/audio/transcribe`.

**3) Whisper via transformers.js (WebGPU/WASM) — a rede de segurança.** Gratuito para sempre, sem cota, sem chave, funciona offline e resolve o caso em que o áudio é longo demais, sensível, ou a cota do Groq estourou. Custo: ~85 MB de pesos ONNX baixados uma vez (cacheáveis no próprio nginx do Decrypter, sem CDN externo, via `env.remoteHost`). Carregue como *chunk* dinâmico, nunca no bundle inicial.

**O que eu NÃO faria:** Google Cloud STT (exige cartão para 60 min/mês — péssima troca), Vosk (modelo pt-BR tem WER de 32–69%, é lixo para cifras onde cada letra conta, e a lib do navegador está sem manutenção há 4 anos), ElevenLabs e Hugging Face (cotas grátis simbólicas). Deepgram e AssemblyAI são ótimos e sem cartão, mas são **créditos únicos** ($200 e $50) — guarde como reserva estratégica, não como base.

- **Web Speech API (SpeechRecognition) com start(audioTrack) — arquivo direto no navegador** — Reconhecimento de fala nativo do navegador. Desde o Chrome 135 o start() aceita um MediaStreamTrack opcional, o que permite alimentar um ARQUIVO: cria-se um <audio> com o arquivo, chama-se captureStream(), pega-se getAudioTracks()[0] e passa-se para recognition.start(track). O próprio exemplo oficial do MDN faz exatamente isso com um mp3. Devolve texto + confidence via evento 'result'. Por padrão o Chrome manda o áudio para os servidores do Google; com processLocally=true (Chrome 139+) roda 100% no dispositivo, e pt-BR está na lista de idiomas on-device.
  - https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/start
  - gratuito: `sim-ilimitado` · cartão: não · limites: Sem chave, sem cota medida, sem conta. O Google declara que o reconhecimento é oferecido 'sem limite de requisições' a sites rodando no Chrome, desde que se respeite os Termos do Chrome (isso vale para a API do navegador; a Speech API por chave HTTPS própria é limitada a 50 req/dia e é OUTRA coisa). Limites práticos reais: (a) a sessão da nuvem encerra em torno de 60 s — para áudio longo é preciso continuous=true e reiniciar, e reinícios agressivos levam a throttling; (b) roda em TEMPO REAL — áudio de 4 min leva 4 min; (c) tamanho de arquivo é irrelevante (nada sobe), só a duração importa. Suporte: audioTrack em Chrome 135+ e Edge 135+ apenas. Firefox e Safari NÃO suportam o parâmetro audioTrack (Safari tem SpeechRecognition só por microfone desde 14.1; Firefox 142+ atrás de flag). processLocally/available()/install() = Chrome 139+.
  - integra: 100% no NAVEGADOR, zero backend, zero bytes de biblioteca no bundle. Passo a passo na aba Áudio: (1) usuário solta o arquivo; (2) `const el = new Audio(URL.createObjectURL(file))`; (3) no evento 'canplay': `const track = el.captureStream().getAudioTracks()[0]`; (4) `const r = new (window.SpeechRecognition ?? window.webkitSpeechRecognition)(); r.lang='pt-BR'; r.continuous=true; r.interimResults=true;` (5) `el.play(); r.start(track)`; (6) concatenar `event.results[i][0].transcript` no evento 'result' e jogar o texto acumulado direto no Decodificador. Detecção de suporte obrigatória: se `!('SpeechRecognition' in window || 'webkitSpeechRecognition' in window)` esconda o botão; teste também o audioTrack com try/catch de InvalidStateError. Para modo offline: `await SpeechRecognition.available({langs:['pt-BR'], processLocally:true})` → se 'downloadable', chame `SpeechRecognition.install(...)` e só então `r.processLocally = true`. Sem CORS envolvido — não há requisição HTTP sua.
  - esforço: baixo — meio dia; ~80 linhas de TS e um hook. É o melhor retorno por linha de código de toda a categoria. · risco: O track precisa ter readyState 'live' e kind 'audio', senão InvalidStateError. O áudio precisa estar TOCANDO — se o elemento for mudado/mutado o captureStream pode entregar silêncio (não confirmado; se der problema, roteie por um AudioContext com GainNode em 0 e MediaStreamAudioDestinationNode). Acelerar com playbackRate=2 para ganhar tempo degrada a precisão (não testado). O corte de ~60 s é o incômodo real em áudios longos — resolvido reiniciando ou usando processLocally. Chrome pode mudar a política de uso gratuito a qualquer momento, e no modo nuvem o áudio da prova SAI da máquina para o Google (relevante se a prova for sigilosa). Firefox/Safari ficam de fora: sempre ofereça uma segunda rota.

- **Groq — Whisper Large v3 Turbo (via backend .NET)** — API de transcrição hospedada rodando whisper-large-v3-turbo em hardware LPU. Recebe o arquivo por multipart/form-data e devolve JSON, verbose JSON (com timestamps) ou TEXTO PURO — o response_format=text entrega exatamente a string que o Decodificador quer. Concretamente: (1) `src/TheDecrypter.Domain/Gateways/ISpeechToTextGateway.cs` com `Task<string> TranscribeAsync(Stream audio, string fileName, string lang, CancellationToken ct)`, espelhando `IWhat3WordsGateway.cs`; (2) `src/TheDecrypter.Http/Gateways/GroqSpeechGateway.cs` fazendo POST em https://api.groq.com/openai/v1/audio/transcriptions com `Authorization: Bearer {GROQ_API_KEY}`, MultipartFormDataContent com os campos file, model=whisper-large-v3-turbo, language=pt, response_format=text — mesmo estilo do `What3WordsGateway.cs`; (3) `src/TheDecrypter.Api/Controllers/AudioController.cs` com [Authorize] (o login por token já existe), recebendo IFormFile e devolvendo `{ text }`; chave em variável de ambiente, nunca no front. Não chame a Groq direto do navegador: a lib oficial exige a flag `dangerouslyAllowBrowser` justamente porque isso expõe a chave secreta no bundle. Antes de subir, converta no navegador para mono 16 kHz (WebAudio + encoder FLAC/Opus wasm, ~50 KB) e o teto de 25 MB deixa de existir na prática (~4 h de áudio).
  - esforço: baixo/médio — 1 dia. Um gateway, um controller, um input de arquivo. A maior parte do trabalho é a conversão/compressão opcional no cliente. · risco: Cota diária generosa MAS compartilhada por toda a instância — se o Decrypter tiver vários usuários, um áudio longo de um usuário come a cota. Mitigue guardando o hash do arquivo no cache que já existe (`TheDecrypter.Cache`) para não retranscrever o mesmo áudio. A Groq mudou preços e limites de free tier mais de uma vez; confirme em console.groq.com/settings/limits antes de contar com os números. Whisper alucina em silêncio e em ruído puro — para 'som ambiente' ele vai inventar frases (use vad/no_speech_threshold ou trate como sinal de que o áudio não é fala). O free tier não dá garantia de retenção zero dos dados.

- **Whisper no navegador via transformers.js (WebGPU + WASM)** — Roda o Whisper inteiro dentro do navegador com ONNX Runtime Web, via `pipeline('automatic-speech-recognition', 'onnx-community/whisper-base')`. Aceita arquivo (decodifica com AudioContext para Float32Array 16 kHz), devolve texto e opcionalmente timestamps. Com `device:'webgpu'` usa a GPU; sem WebGPU cai para WASM e funciona igual, só mais devagar. Depois do primeiro download não precisa mais de internet.

Peso dos MODELOS (baixados uma vez e cacheados): whisper-tiny ~40 MB (q4/q8); whisper-base ~85 MB na combinação recomendada (encoder q4 ~18,7 MB + decoder q4f16 ~66 MB), ou ~145–200 MB em fp32/int8; whisper-small ~240 MB. Peso da BIBLIOTECA no bundle: @huggingface/transformers + onnxruntime-web, centenas de KB de JS mais os .wasm — precisa ser chunk dinâmico. WebGPU exige Chrome 113+ com GPU compatível e dá 5–10× sobre WASM. Suporte multilíngue inclui português (use os modelos multilíngues, NÃO os `.en`).
  - integra: 100% no NAVEGADOR, mas com um cuidado que o CLAUDE.md do repo cobra: NADA de CDN. Por padrão a lib busca pesos em huggingface.co e os .wasm no jsDelivr — os dois precisam ser redirecionados para o próprio domínio: `env.allowRemoteModels=false; env.localModelPath='/models/'; env.backends.onnx.wasm.wasmPaths='/ort/'`, e você copia os arquivos ONNX + .wasm para `public/` (servidos pelo nginx.conf que já está no repo) ou serve pelo backend .NET como estáticos. Rode SEMPRE em Web Worker (`new Worker(new URL('./whisper.worker.ts', import.meta.url), {type:'module'})`), senão a UI congela. Importe com `await import('@huggingface/transformers')` dentro do worker para que o Vite gere um chunk separado — o `dist` do Decrypter não pode engordar para quem nunca abre a aba Áudio. Backend: nenhum, exceto servir os arquivos estáticos. Mostre barra de progresso do download do modelo (a lib emite callback de progresso), senão parece travado.
  - esforço: médio — 2 a 3 dias. O worker, o pipeline de decodificação de áudio, o cache dos pesos, o fallback WASM e o aviso de download são cada um uma peça pequena, mas somam. · risco: O download inicial de ~85 MB é uma barreira psicológica no meio de uma prova de gincana cronometrada — pré-carregue antes do evento. Em WASM sem WebGPU o áudio de 5 minutos pode levar minutos numa máquina modesta. Armadilha documentada: quantizar o ENCODER para q8 degrada as features e gera saída embaralhada, principalmente com sotaque e ruído — use encoder fp32 (ou q4) com decoder quantizado. Consumo de RAM alto; whisper-small é o teto prático no navegador. A API do transformers.js quebrou entre v2 e v3; fixe a versão no package.json.

### Identificação de SONS que não são música ("que som é este?" — sirene, animal, máquina, instrumento)

**Recomendada:** **Vale a combinação: AST-AudioSet no navegador + BirdNET-tfjs no navegador + iNaturalist para o nome em português.** Nenhum dos três cobra, nenhum pede cartão, nenhum pede chave, e nenhum manda o áudio da equipe para fora — o que também resolve o problema de latência no meio de uma prova cronometrada.

A ordem de implementação que eu seguiria:

1. **AST (Xenova/ast-finetuned-audioset-10-10-0.4593, q4f16 = 51,4 MB ou q8 = 90,8 MB)** primeiro, porque é o classificador geral: cobre sirene, motor, animal, instrumento, aplauso, trovão — as 521 classes do AudioSet. É o que responde literalmente "que som é este?". Escolhi ele em vez do YAMNet que a pergunta cita porque **não achei um build tfjs do YAMNet publicado hoje** (o tfhub.dev foi aposentado, o Kaggle Models lista só TF2 e TFLite) e porque o AST ganha em qualidade no mesmo eval set: mAP 0,459 contra 0,306. O YAMNet fica como modo "leve" opcional, se os 50–90 MB se mostrarem inviáveis em campo — e nesse caso conte com converter o modelo você mesmo.

2. **BirdNET** depois, porque canto de pássaro é caso frequente em gincana de rua e o AST só sabe dizer "Bird". Os arquivos da demo oficial do Cornell estão acessíveis com CORS aberto (`model.json` de 0,89 MB + 13 shards de 4 MB = ~51,3 MB + rótulos de 0,26 MB com 6.521 espécies) — **espelhe em `public/`, não faça hotlink**, e respeite a CC BY-NC-SA 4.0 dos pesos (o README diz que uso educacional conta como não comercial, então está coberto, mas exige atribuição visível).

3. **iNaturalist** é o remate barato: `/v1/taxa?q=<científico>&locale=pt-BR` sem chave, CORS aberto, meio dia de trabalho, e transforma `Ramphastos toco` em `Tucano-toco`. Testado agora e funcionando. Ainda melhor: pré-gere o mapeamento das espécies brasileiras num JSON offline e nem dependa de rede.

**Duas armadilhas que valem mais que as recomendações:**

O **Freesound** parece perfeito no papel — busca por similaridade, descritores do Essentia, 2.000 req/dia grátis — e a parte de **busca textual realmente vale** (proxy simples no .NET, algumas horas, ótimo para conferir de ouvido o palpite do AST). Mas a **busca por similaridade a partir do áudio do usuário está efetivamente fechada**: não existe endpoint que analise arquivo arbitrário, o espaço `laion_clap` exige o vetor 512-d L2-normalizado do checkpoint `630k-audioset-fusion-best.pt`, e o único port ONNX pronto para navegador é o **unfused** — espaço diferente, que devolveria resultados plausíveis e errados sem falhar. Sobre o outro espaço, os próprios docs admitem: "We currently don't provide code to extract these features from arbitrary audio". Se for tentar, o primeiro passo é o teste de sanidade, não o código: pegue um som do Freesound, baixe o vetor oficial por `/apiv2/sounds/<id>/analysis/`, calcule o seu localmente, e só siga se o cosseno der ~1,0.

E o **Macaulay/Merlin não tem API de identificação** — nem pública nem negociável. O equivalente técnico é o BirdNET, do mesmo laboratório da Cornell, aberto. Fechada essa pergunta, não gaste tempo procurando.

Uma nota transversal sobre o caso de uso: esses classificadores devolvem rótulos genéricos em inglês ("Siren", "Emergency vehicle", "Toco Toucan"). Isso quase nunca é a resposta literal da prova — é **pista**. Projete a aba mostrando sempre o top-5 com as confianças e um botão "mandar para o Decodificador" em cada linha, em vez de cravar um palpite único. E como o **CLAP zero-shot** (34,3 MB só do encoder de áudio, com os embeddings de texto pré-computados offline) deixa a equipe digitar as próprias hipóteses, ele é o complemento mais interessante para uma fase 2 — é o único que se adapta ao enunciado da prova em vez de impor um vocabulário fixo.

- **CLAP zero-shot no navegador (você escreve os rótulos candidatos)** — CLAP põe áudio e texto no MESMO espaço vetorial de 512 dimensões. ### Metadados e catálogos musicais (título ↔ letra ↔ álbum/ano)

**Recomendada:** Combinação de TRÊS, nesta ordem — e uma ressalva que muda o desenho da aba.

**A ressalva primeiro, porque é o achado mais importante: nesta categoria NÃO EXISTE opção gratuita que faça letra→título.** Testei um a um. O LRCLIB parece fazer, mas não faz — comprovei que `?q=` só casa com título/artista/álbum (busquei o verso 'Nosso suor sagrado' → 0 resultados; 'Bohemian Rhapsody' → 20). O Genius não devolve letra pela API e o endpoint público sem token responde 403 para IP de servidor. O ChartLyrics, que os tutoriais ainda recomendam para isso, está morto (404 verificado). O Musixmatch é o único com busca por trecho de letra, e o plano grátis dele está sob suspeita (o portal de desenvolvedor agora redireciona para 'Pro API'), além de entregar só 30% do texto. Conclusão prática: **quando a prova for 'trecho de letra → nome da música', o caminho é um buscador web, não um catálogo musical** — trate isso como assunto de outra categoria e não gaste esforço aqui.

Para o caminho que de fato funciona (áudio → transcrição/título → letra e metadados), monte o pipeline assim:

1. **iTunes Search API — o limpador de nome.** Direto do navegador, CORS `*` confirmado, sem chave e sem cartão. O texto que sai de uma transcrição de voz vem torto e sem acento; joguei exatamente isso ('tempo perdido legiao urbana') e ele devolveu título, artista, álbum e ano corretos. É o passo que transforma palpite sujo em nome limpo. Custo: uma hora.

2. **LRCLIB — a fonte de letra, e a melhor descoberta da pesquisa.** Sem chave, sem cadastro, sem cartão, sem cota (20 chamadas seguidas, 20 respostas 200), CORS `*` confirmado, e entrega letra em texto puro E sincronizada, com boa cobertura brasileira. Zero backend, zero segredo, zero peso no bundle. É literalmente `fetch()` — o que entra em choque com nada da arquitetura atual. O `plainLyrics` cai direto no Decodificador e passa pelas ~100 cifras. Custo: uma hora. Ponha o **lyrics.ovh** como plano B de três linhas para quando o LRCLIB der 404, ciente de que é serviço de hobby.

3. **MusicBrainz via backend — a autoridade sobre ano e álbum.** Só quando a resposta da prova for uma data ou um álbum, porque aí você quer a fonte canônica, não a loja da Apple. Este é o único que merece código no .NET, e o molde já está pronto: é o `NominatimGateway` copiado — mesma exigência de User-Agent identificável (que o navegador **não** consegue mandar, pois `User-Agent` é forbidden header no fetch), mesmo rate-limiter de ~1 req/s no Polly, mesma linha em `HttpDependencyInjection.cs`, mesma exposição no `LookupsController` que já tem `[Route("api")]`. Custo: meio dia.

**O que deixar de fora:** Last.fm (não tem letra, cota sem número publicado, e ainda obriga o selo 'powered by AudioScrobbler' na tela — entrega menos que os três acima); Genius (a letra só sai raspando HTML, contra os termos deles); Deezer (precisa de proxy, verifiquei que não manda `access-control-allow-origin`, e entrega o mesmo que o iTunes entrega de graça no navegador); Musixmatch e ChartLyrics pelos motivos acima. O **Discogs** é o único descartado com ressalva: guarde-o para quando a prova perguntar sobre a mídia física (número de catálogo, gravadora, ano da prensagem brasileira) — nesse nicho ele não tem concorrente, roda direto do navegador sem token a 25 req/min (`x-discogs-ratelimit: 25`, verificado) e o CORS é liberado.

### O que o NAVEGADOR faz sozinho, sem API nenhuma (Web Audio, Web Speech, WebCodecs e modelos locais)

**Recomendada:** Ordem de execução: (1) **Web Audio API** — já planejado, custo zero de bundle, é o único que dá TEXTO determinístico (DTMF, Morse por tom) sem inventar nada. (2) **Web Speech API com `start(audioTrack)` + `captureStream()`** — a descoberta que muda o jogo desta categoria: transcrição pt-BR de um arquivo enviado pelo usuário, gratuita, sem chave, sem cartão, sem backend e com ZERO bytes de bundle; o preço é Chrome/Edge desktop apenas (Safari não tem `captureStream`, Firefox não aceita `audioTrack`) e tempo real (5 min de áudio = 5 min de espera). Ligar `processLocally` quando `available({langs:['pt-BR']})` disser que dá, com o caminho em nuvem como fallback e aviso explícito. Somar `phrases` (Chrome 142+) com o vocabulário da prova é ganho de acerto de graça. (3) **MediaPipe/YAMNet** (~11 MB: 4,13 MB de modelo + 6,58 MB de wasm) se e quando aparecer prova de som ambiente — melhor relação capacidade/peso da categoria. **O ponto em que o modelo local fica grande demais:** a régua não é o bundle inicial (todos são carregados sob demanda), é o download único que uma equipe faz no 4G no meio da gincana. Até ~10 MB é invisível (YAMNet, Silero-VAD, essentia.js). Até ~80 MB é defensável se for um botão explícito com barra de progresso (whisper-base int8 = 76,9 MB + 11,8 MB de runtime ORT ≈ 89 MB no primeiro uso). **A linha vermelha está em whisper-small (249,1 MB)** — é onde a qualidade em pt-BR começa a ficar boa e é exatamente onde o peso deixa de ser justificável para um app que preza por bundle enxuto; `large-v3-turbo` (563,5 MB no melhor caso) está fora de discussão. E, se a decisão for por Whisper, o custo escondido não é o MB: é que ligar COOP/COEP para ter threads pode quebrar os tiles do Leaflet no Safari — colidindo com a regra de que a visão mobile não regride. Whisper local só se paga se o requisito for transcrever SEM depender de Google/Apple; se a dependência for aceitável, o item (2) entrega o mesmo texto por meio dia de trabalho e zero MB.

- **Web Audio API — decodeAudioData + OfflineAudioContext + AnalyserNode (o que já está no PLANO-AUDIO.md)** — Decodifica mp3/aac/m4a/wav/ogg em PCM Float32, dá espectrograma (STFT própria), inversão, mudança de velocidade, e é a base dos detectores determinísticos que JÁ produzem texto: DTMF (dígitos), Morse por tom (pontos e traços), leitura de chunks RIFF. É a única categoria daqui que cospe texto para o Decodificador sem modelo nenhum e sem rede.
  - https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData
  - gratuito: `sim-ilimitado` · cartão: não · limites: Sem cota, sem chave, sem rede. Tetos reais são de memória e não de licença: AudioBuffer Float32 planar = 22,0 MB por 60 s estéreo, ~1,27 GB por hora (medido no repo). Canvas do iOS Safari estoura em 16.777.216 px e falha em SILÊNCIO (3 min a N=2048/hop=512 = 17,3 Mpx). Nenhum navegador grava WAV pelo MediaRecorder — o RIFF de 44 bytes é escrito à mão (20,2 ms para 60 s mono).
  - integra: 100% no navegador, zero bytes de bundle, zero backend. Já existe base no repo (src/features/audio/lsb.ts e container.ts). A STFT tem de ir para Worker acima de ~3 s de áudio (Vite tem Worker nativo: new Worker(new URL('./stft.worker.ts', import.meta.url), { type: 'module' })), devolvendo Uint8Array transferível e não Float32.
  - esforço: médio — o plano existe e está fatiado; é execução, não pesquisa · risco: Duas armadilhas silenciosas já documentadas no repo e que valem repetir: (1) decodeAudioData REAMOSTRA sempre para a taxa do AudioContext, e AudioBuffer.sampleRate já é a taxa do contexto — a taxa original do arquivo não é exposta por API nenhuma. Um tom de 30 kHz num arquivo de 96 kHz cai ~54 dB num contexto de 48 kHz e a faixa alta aparece vazia com toda a cara de estar correta. (2) decodeAudioData faz DETACH do ArrayBuffer de entrada (176.444 → 0 bytes, medido): quem ler os bytes crus depois recebe comprimento 0, sem erro, passando por TypeScript e Biome. Defesa: slice(0) antes.

- **Web Speech API com arquivo — recognition.start(audioTrack) + HTMLMediaElement.captureStream()** — É a resposta direta ao caso 'alguém fala uma frase e o texto é a resposta'. Desde o Chrome 135 o start() aceita um MediaStreamTrack, então dá para transcrever um ARQUIVO enviado pelo usuário: cria-se um <audio> com o objectURL, chama-se captureStream(), pega-se getAudioTracks()[0] e passa-se ao start(). Devolve texto pt-BR pronto para cair na Cadeia do Decodificador. Zero bytes de bundle, zero chave, zero backend.
  - https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/start
  - gratuito: `sim-ilimitado` · cartão: não · limites: CONCRETO, medido no browser-compat-data da MDN hoje: SpeechRecognition.start com parâmetro audioTrack = Chrome 135+, Edge espelha, Firefox NÃO, Safari NÃO. HTMLMediaElement.captureStream = Chrome 62+, Firefox 149+, Safari NÃO existe. Ou seja: o caminho arquivo→texto é Chrome/Edge desktop, e só. Custo de TEMPO REAL: o áudio precisa ser TOCADO (audioElement.play()) — 5 minutos de arquivo levam 5 minutos de transcrição; não há modo offline/acelerado. Sem processLocally, o áudio vai para os servidores do Google: no Chrome não há limite de uso documentado e não há chave, mas fora do Chrome oficial (Chromium/Electron/WebView) o endpoint exige chave de desenvolvedor limitada a 50 requisições/dia. A transcrição também pode parar sozinha após silêncio longo — use continuous=true e interimResults=true.
  - integra: Tudo no navegador, nada passa pelo backend .NET. Não há CORS envolvido porque não é fetch: o navegador fala com o serviço do próprio fabricante. Padrão: const el = new Audio(URL.createObjectURL(file)); el.addEventListener('canplay', () => { const t = el.captureStream().getAudioTracks()[0]; el.play(); rec.start(t); }); el.onended = () => rec.stop(). Detecção de capacidade obrigatória: 'captureStream' in HTMLMediaElement.prototype && SpeechRecognition (sem isso o botão tem de sumir, não falhar). Bônus do Chrome 142+: recognition.phrases aceita viés contextual — dá para injetar o vocabulário da prova (nomes de rua de Blumenau, termos da gincana) e melhorar o acerto sem custo.
  - esforço: baixo — meio dia; é a melhor relação valor/peso de toda esta categoria · risco: (a) O texto que sai é do Google, não do dispositivo: privacidade e dependência de um serviço não documentado que a Google pode mudar sem aviso — é 'sem API' no sentido de não ter chave, não no sentido de não ter terceiro. (b) Chrome/Edge apenas: numa gincana com celular Safari/iPhone o botão não existe. (c) O modo tempo-real transforma um áudio de 10 min numa espera de 10 min com a aba precisando ficar viva. (d) Pontuação: o reconhecimento entrega texto pt-BR já 'limpo' (maiúsculas, acentos, sem pontuação a menos que unspokenPunctuation, Chrome 151+) — para as ~100 cifras isso é BOM (texto natural), mas se a prova esconder a resposta na grafia exata, a normalização pode destruí-la. Sempre mostrar o texto cru e deixar a pessoa editar antes de mandar ao Decodificador.

- **Web Speech API 100% no dispositivo — processLocally + SpeechRecognition.available()/install() (SODA)** — Mesma API do item anterior, mas com recognition.processLocally = true: o áudio nunca sai da máquina. O modelo (pacote de idioma SODA) é baixado e gerenciado pelo PRÓPRIO navegador, não pelo seu bundle — é o único jeito de ter modelo local com custo de bundle igual a zero. available({langs:['pt-BR'], processLocally:true}) devolve 'available' | 'downloadable' | 'downloading' | 'unavailable'; install() dispara o download e resolve quando termina.

### APIs de geração e manipulação de áudio (o lado inverso: sintetizar para conferir uma hipótese)

**Recomendada:** Vale a Web Audio API pura (OscillatorNode + OfflineAudioContext + um encoder WAV de ~40 linhas). É a única opção que atende os quatro critérios ao mesmo tempo e com folga: gratuita de verdade e para sempre, sem cartão, sem chave, sem rede, ZERO bytes de bundle, e funciona 100% offline com o arquivo local. Ela cobre o caso real desta categoria — gerar DTMF, Morse, tons e varreduras para conferir uma hipótese — e fecha o ciclo com o que o repo já tem: `src/features/audio/fft.ts` já traz `goertzel()` (o comentário na linha 130 diz que é o que serve para DTMF) e `src/features/decoder/engine/codecs.ts:293` já registra `encodeMorse`. Falta só transformar pontos e traços em envelopes de oscilador. De brinde, sintetizar sinais conhecidos vira teste automatizado dos detectores em `fundacao.test.ts` — gerar um DTMF de dígito sabido e cobrar do Goertzel a resposta certa.

Como complementos, nesta ordem: (a) `speechSynthesis` para o botão "ouvir a hipótese em voz alta" — uma hora de trabalho, zero dependência, mas ciente da limitação dura de que o áudio NÃO é capturável e portanto não alimenta o Decodificador; (b) `decodeAudioData` como porta de entrada de qualquer arquivo enviado, alimentando o STFT que já existe.

Se um dia for preciso TTS de verdade com voz pt-BR e ARQUIVO capturável, o caminho é VoiceRSS atrás do backend .NET (350 req/dia, 100 KB por requisição, "no payment information" confirmado na página de preços deles) — é a única hospedada decente que não pede cartão, e o padrão de proxy já está pronto em `src/lib/what3words.ts` + a rota equivalente no the-decrypter-api. Google Cloud (4M caracteres/mês Standard, permanente) só se aceitarem habilitar faturamento com cartão.

Três descartes com motivo: Puter.js promete o melhor ("free unlimited") mas exige script de CDN em runtime e login Puter do operador — colide de frente com a regra de bundle deste repo. Kokoro-js e Piper são tecnicamente lindos e têm voz pt-BR, mas custam 63–160 MB de modelo auto-hospedado para um recurso que raramente resolve prova. E o que MUDOU: a Hugging Face, que era a saída gratuita óbvia para inferência, hoje dá US$ 0,10/mês de crédito na conta gratuita; o endpoint de TTS da StreamElements, por anos aberto e sem chave, agora exige token; e o Polly é trial de 12 meses, não cota permanente como Google e Azure.
